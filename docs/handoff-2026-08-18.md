## 2. 지금까지 만든 것 (기능 단위로)

### 2-1. 공공데이터 API 연동 (7개 소스)
정부 Open API 7개를 실시간으로 불러와 하나의 공통 타입(`WelfareItem`)으로 합칩니다.

| 소스 키 | 실제 API | 비고 |
|---|---|---|
| `central` | 한국사회보장정보원 · 중앙부처복지서비스 | XML, "자립"/"청년" 키워드로 각각 검색 후 병합 |
| `local` | 한국사회보장정보원 · 지자체복지서비스 | XML, 위와 동일하게 키워드 두 번 검색 |
| `gov24` | 정부24(보조금24) | JSON, 키워드 두 번 검색 |
| `housing` | 마이홈포털 공공임대주택 모집공고 | JSON(odcloud.kr 형식), 키워드 검색 없이 전체 수집 후 텍스트 필터 |
| `training` | 고용24 · 국민내일배움카드 훈련과정 | XML, 전체 수집 후 텍스트 필터 |
| `jobseekerProgram` | 고용24 · 구직자취업역량강화프로그램 | XML, 전체 수집 후 텍스트 필터 |
| `dualTraining` | 고용24 · 일학습병행 훈련과정 | XML, 전체 수집 후 텍스트 필터 |

- 공용 로직은 `lib/govApis.ts`에 모아뒀고 (`app/api/welfare/route.ts`와
  `app/api/sync-announcements/route.ts` 양쪽에서 재사용), 소스마다 응답 포맷이 달라서
  (`<servList>`/`<scn_list>`/`<empPgmSchdInvite>` XML 블록, JSON envelope, odcloud 플랫 JSON)
  각각 다른 매퍼 함수로 `WelfareItem` 공통 타입으로 변환합니다.
- "자립준비청년 관련"과 "청년 관련"을 각각 텍스트 키워드로 판별하는 `isAboutCareLeavers` /
  `isAboutYouth` 함수가 있고, 화면에서 3단계 토글(자립준비청년 관련 / 청년 관련 / 전체)로
  볼 수 있습니다 (`app/page.tsx`의 `ApiPreviewScreen`).
- **주의**: 이 분류는 100% 법적 판단이 아니라 텍스트 키워드 기반 MVP 근사치입니다.

### 2-2. 자격 정밀 진단 (F1/F2)
- 온보딩 12문항 (`app/data/eligibility.ts`의 타입/라벨, UI는 `app/components/EligibilityFlow.tsx`의
  `EligibilityOnboarding`)
- **처음에는 21개 프로그램짜리 목업 데이터(`PROGRAMS`, `evaluateAll`)로 만들었다가, 이후

  `WelfareItem[]`을 텍스트 규칙(지역/보호기간/재학여부/무주택/기초생활수급/현재 보호중 여부/중복
  지원 여부)으로 매칭해서 결과 화면(`EligibilityResultScreen`)에 보여줍니다.
- **버그 수정 이력**: 지역명 매칭에서 축약형 지역명(충북/충남/경북/경남/전남)이 정식 명칭
  (충청북도/충청남도/경상북도/경상남도/전라남도)의 부분 문자열이 아니라서 매칭이 안 되던 버그를
  발견 → 정식 명칭을 먼저 검사하고 못 찾으면 축약형을 검사하도록 수정 (테스트로 26건→13건 정상화
  확인).

### 2-3. DB 저장/검수 파이프라인 (오늘 새로 만든 부분, 진행 중)
사용자가 "API를 바로 쓰기엔 검수도 하고 싶고 중복도 있는 것 같다"고 해서, Supabase에
저장·검수하는 구조를 오늘 새로 만들었습니다.

- **`lib/supabase.ts`**: `supabase`(공개 anon 클라이언트, env 없으면 `null`)와
  `createSupabaseAdminClient()`(서비스 롤 클라이언트, RLS 우회용) 두 가지를 export.
- **`supabase/schema.sql`** (v2): 소스별로 테이블 7개를 따로 만듭니다
  (`announcements_central`, `announcements_local`, `announcements_gov24`,
  `announcements_housing`, `announcements_training`, `announcements_jobseeker_program`,
  `announcements_dual_training`). 각 테이블 컬럼 구성:
  - 원문 필드: `source_id`(고유), `serv_nm`, `serv_dgst`, `org`, `region`, `target_traits`,
    `deadline`, `link`, `raw_data`(jsonb)
  - **온보딩 질문 매칭용 분류 컬럼** (저장 시점에 미리 계산해서 굳혀둠):
    `mentions_care_leaver`, `mentions_youth`, `protection_years_limit`,
    `requires_enrolled`, `requires_no_home`, `requires_basic_livelihood`,
    `requires_already_ended`, `region_scope`, `interest_categories`,
    `protection_end_types_applicable`(보호종료 유형 5종 중 해당하는 것)
  - **검수 워크플로우 컬럼**: `review_status`(pending/approved/rejected),
    `duplicate_of_source`, `duplicate_of_source_id`, `reviewed_by`, `reviewed_at`, `review_note`
  - `pg_trgm` 확장으로 이름 유사도 기반 중복 탐지 인덱스, RLS로 `review_status='approved'`인
    것만 익명 조회 가능하도록 정책 설정, 전체 통합 뷰 `announcements_all` 포함.
- **`app/data/classify.ts`**: 공고 원문에서 위 분류 컬럼들을 자동으로 뽑아내는
  `classifyItem(item)` 함수. `realMatch.ts`가 화면에서 매번 하던 텍스트 검사를 저장 시점에
  한 번만 계산해두는 것.
  - ⚠️ **알려진 한계**: `protectionEndTypesApplicable`은 아직 항상 5종 전부를 반환하는
    placeholder입니다 (본문에서 배제 신호를 찾아 실제로 걸러내는 로직은 미구현).
- **`app/api/sync-announcements/route.ts`**: 7개 소스를 모두 fetch해서 Supabase에 upsert하는
  API 라우트.
  - `central`/`local`/`gov24`는 "자립" 키워드 검색 결과를 필터링 없이 그대로 다 저장
    (노이즈는 나중에 사람이 `review_status`로 검수).
  - `housing`/`training`/`jobseekerProgram`/`dualTraining`은 서버 단 키워드 검색이 없는
    API라 (수백~수만 건 규모) `isAboutCareLeavers`로 미리 걸러서 저장.
  - 재동기화 시 검수 상태(`review_status` 등)를 덮어쓰지 않도록, upsert 페이로드에서 검수
    관련 컬럼은 의도적으로 제외 (Supabase가 생성하는 `ON CONFLICT DO UPDATE SET`이 페이로드에
    있는 컬럼만 갱신하는 걸 이용).

## 3. 지금 당장 막혀 있는 것 (다음 세션에서 바로 이어서 할 일)

1. **Supabase 프로젝트에 스키마가 아직 없음.**
   사용자의 실제 Supabase 프로젝트(`https://hoemgmadhkzfeqjejgfg.supabase.co`)에
   `supabase/schema.sql`을 SQL Editor에서 실행한 적이 없습니다. 마지막 라이브 테스트에서
   `"Could not find the table 'public.announcements_central' in the schema cache"` 에러가
   났습니다. → **사용자가 Supabase 대시보드 → SQL Editor에서 `supabase/schema.sql` 전체를
   붙여넣고 실행해야** 다음 단계 진행 가능.
2. 스키마 실행 후 `/api/sync-announcements`를 다시 호출해서 7개 테이블에 실제로 행이
   들어가는지 확인 필요.
3. `app/api/sync-announcements/route.ts`의 `syncSource()` 시그니처를
   `(supabase, source, rawFetchedCount, candidateItems)`로 바꾸고 호출부도 전부 맞춰서
   수정 완료했고, `npx tsc --noEmit`으로 컴파일 에러 없음을 확인함 (이 부분은 이미 해결됨,
   재작업 불필요).

## 7. 이어받을 때 확인할 순서 (체크리스트)

1. `git status`, `git log --oneline -10`으로 최신 커밋 상태 확인 (이 세션 작업은 아직
   커밋 전일 수 있음 — 사용자가 명시적으로 커밋 요청 안 했으면 커밋하지 말 것).
2. `npx tsc --noEmit`으로 타입 에러 없는지 확인.
3. 사용자에게 "Supabase에 schema.sql 실행했는지" 먼저 물어보기 — 안 했으면 그것부터 안내.
4. 실행했다면 `/api/sync-announcements` 호출해서 실제 저장 확인 후, 저장된 데이터를 화면에서
   보여주는 조회 API/화면(아직 미구현)을 만들지 논의.
