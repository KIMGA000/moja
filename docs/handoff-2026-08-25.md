## 1. 프로젝트 개요

- **서비스명**: 모자(MOJA), 팀명: 파란만 (AX-Ton 해커톤)
- **대상 사용자**: 자립준비청년 (보호시설·위탁가정에서 보호가 종료되어 자립을 준비/시작한 청년)
- **핵심 가치**: 흩어진 정부 지원 공고를 실시간으로 모아 조건에 맞는 것만 보여주고, 자격 여부를
  진단해주고, 로그인하면 개인화된 정보를 계속 보여주고, 또래와 이야기 나눌 수 있는 익명
  커뮤니티도 제공
- **기술 스택**: Next.js 15(App Router) + React 19 + TypeScript, Supabase(PostgreSQL + Auth),
  카카오 로그인(OAuth), Vercel 배포 + Vercel Cron

## 2. 지금까지 만든 기능

### 2-1. 공공데이터 API 연동 → DB 저장 → 화면은 DB만 읽음 (중요한 구조 변경)

**이전에는 화면(자격 진단)이 방문마다 8개 공공 API를 직접 호출했는데, API 호출 한도 문제로
지금은 완전히 DB 기반으로 바뀌었습니다.**

- `lib/govApis.ts`: 8개 소스 공용 fetch/파싱 로직 (기존과 동일)
- `app/api/sync-announcements/route.ts`: 8개 API를 조회해서 Supabase DB에 upsert.
  - **새로 동기화되는 공고는 검수 없이 바로 `review_status='approved'`로 들어감** (검수 UI가
    아직 없어서 임시 조치 — 기존에 사람이 검수해둔 값은 재동기화해도 안 건드림)
  - **매일 새벽 5시(KST)에 Vercel Cron이 자동 호출** (`vercel.json`, UTC 20:00 = KST 05:00)
  - `CRON_SECRET` 환경변수를 설정해두면 그 값으로 요청을 검증함(선택, 아직 미설정)
- `app/api/announcements/route.ts`: **화면이 실제로 쓰는 건 이 라우트 하나.** DB
  (`announcements_all` 뷰)에서 `review_status='approved'`이고 **최근 3일 안에 동기화 때
  다시 확인된**(=API에서 아직 사라지지 않은) 공고만 반환. `classify.ts`가 계산해둔
  `regionScope`/`requiresEnrolled`/`interestCategories`/`descriptionTags`도 raw_data와
  함께 내려줌.
- `app/api/welfare/route.ts`: 옛날 방식(라이브 API 직접 호출, DB 미사용)이 아직 남아있음.
  **랜딩화면의 "🔎 실시간 공공데이터 API 결과 보기" 버튼 전용이고, 사용자가 "이건 API 테스트용,
  나중에 지울 것"이라고 명시함.** 실제 서비스 로직과는 무관.

### 2-2. 카카오 로그인 + 개인화 (이번에 새로 추가)

- **Supabase Auth의 Kakao Provider**로 로그인. 신원인증(진짜 자립준비청년인지 확인)은 없음 —
  "이 저장된 데이터가 같은 사람 것"임을 보장하는 최소 계정 계층일 뿐이라는 게 설계 전제.
- `app/hooks/useAuthSession.ts`: 세션 훅 (`useAuthSession`) + 닉네임 추출(`getNickname`,
  카카오 프로필의 name/nickname/preferred_username/full_name 순으로 시도)
- `app/components/AuthBar.tsx`: 헤더의 로그인/로그아웃 버튼. 로그인하면 `profiles` 테이블에
  닉네임 upsert.
- **개인화 홈**: 로그인 + 저장된 진단 결과가 있으면 **랜딩 화면 자체가 개인화 결과 화면으로
  바뀜** (더 이상 "내 자격 정밀 진단하기" 버튼을 눌러야 하는 게 아님). 위에 "🔁 진단 다시하기"
  / "💬 커뮤니티" 링크 항상 노출.
- 로그인 상태에서만 보이는 것: 개인화 프로필 카드(지역/현재상태/관심분야 배지 + "정보 수정"),
  D-day 요약 카드(보호종료까지/5년 기한까지), 공고별 관심공고 별표.
- 비로그인 상태에선 그 자리에 "💡 로그인하면 이 진단 결과가 저장되고... 더 개인화해서
  보여드려요" 한 줄만 뜸.
- **DB**: `profiles` 테이블(`id`=auth.users.id, `nickname`, `onboarding_profile` jsonb) —
  본인만 조회/생성/수정 가능한 RLS.

#### 카카오 콘솔 + Supabase 설정 (이미 완료됨, 문제 생기면 여기부터 확인)
- Kakao Developers: REST API 키 발급, 카카오 로그인 활성화, Client Secret 발급+활성화,
  **동의항목 3개 모두 필요**(닉네임/프로필사진/이메일-선택) — 하나라도 빠지면 `KOE205
  (invalid_scope)` 에러남 (Supabase의 카카오 연동이 기본으로 이 3개를 요청하기 때문).
  Redirect URI는 **Supabase 콜백 주소 하나만**(`https://<프로젝트ref>.supabase.co/auth/v1/callback`),
  우리 앱 주소를 여기 넣으면 안 됨(와일드카드도 카카오는 이해 못 함).
- Supabase 대시보드 → Authentication → **URL Configuration**(Providers 화면과는 다른 별도
  메뉴) → **Site URL**과 **Redirect URLs** 둘 다 배포 주소(`https://moja-khaki.vercel.app`,
  `https://moja-khaki.vercel.app/**`)로 설정 필요. **Site URL을 안 바꾸면 배포 사이트에서
  로그인해도 `localhost:3000`으로 리다이렉트되는 버그가 남** (실제로 겪었던 문제).

### 2-4. 자격 진단 결과 화면 — 5개 탭

`app/components/EligibilityFlow.tsx`의 `EligibilityResultScreen`이 이제 탭 5개로 나뉨:

1. **매칭 결과**: 기존 자격 판정(가능성 높음/확인 필요/해당 안 됨). "관심공고만 보기" 토글도
   이 탭에만 있음. 각 공고 설명 아래 `#태그`(2-5 참고) 표시됨.
2. **전체 공고 보기**: DB에 동기화된 공고 전체를 자격 판정 없이 그냥 나열 (필터 없음)
3. **지역별 보기**: 시·도 버튼(기본값 = 내 지역) 선택해서 그 지역+전국 공고만
4. **현재상태별 보기**: 대학재학/대학원재학/취업/미취업/기타 버튼(기본값 = 온보딩 답변) —
   ⚠️ **DB에는 "재학 요건 있음/없음" 이진 플래그(`requiresEnrolled`)만 있어서, 취업/미취업/기타를
   고르면 셋 다 똑같은 결과가 나옴.** 재학 관련 공고 찾을 때만 실질적으로 유용함 — 취업 상태별
   세분화된 데이터는 없음(알려진 한계).
5. **관심분야로 보기**: 관심분야 칩 다중선택(기본값 = 온보딩에서 저장한 관심분야) — DB의
   `interest_categories` 컬럼 기준.

이 중 3/4/5번은 **자격 판정이 아니라 그냥 찾아보기용 필터**라서, 안 맞다고 "못 받는다"는 뜻이
아님 — 매칭결과 탭과는 별개 개념.

### 2-5. 관심공고(북마크) + 클릭 로그

- **북마크**: 로그인 상태면 모든 공고 카드 오른쪽 위에 별표(☆/⭐). `bookmarks` 테이블
  (`user_id`, `source`, `source_id`, **`age_at_action`**, RLS로 본인 것만 조회/추가/삭제).
  - `age_at_action`: 북마크 시점의 만 나이 스냅샷. **정확한 생년월일이 아니라 정수 나이만** —
    나중에 "20대가 어떤 공고에 관심 가졌는지" 같은 **연령대별 집계**를 `user_id` 없이 뽑기
    위한 용도. (`lib/bookmarks.ts`의 `calcAgeFromBirthDate`)
  - "관심공고만 보기" 토글이 매칭결과 탭에 있음.
- **클릭 로그**: "공식 안내 페이지 바로가기" 누르면 `announcement_clicks` 테이블에 익명으로
  기록(어떤 공고인지만, 누가 눌렀는지는 저장 안 함 — insert만 되고 select 정책이 없어서
  service role만 조회 가능).
- **⚠️ 매우 중요한 정책 결정**: 사용자가 "이 데이터를 가공해서 정부에 팔거나, 지역+나이로
  자립준비청년을 식별할 수 있는 지표로 팔 수 있지 않냐"고 제안했었는데, **명시적으로
  거절함** — 취약계층 재식별 위험, 개인정보보호법상 목적 외 이용 문제, 서비스 신뢰 붕괴
  우려 때문. 대신 "개인 식별 없이 집계 형태로 내부 통계 내는 것"까지만 하기로 함. **앞으로
  이 데이터를 다룰 때 이 결정을 뒤집지 말 것** — 특히 `bookmarks`/`announcement_clicks`를
  원본 그대로(비집계) 외부에 공유/판매하는 방향은 다시 제안이 나와도 재확인 필요.

### 2-7. 커뮤니티 — 로그인 연동, 소유권, 수정/삭제

- `community_posts`/`community_comments`에 **`user_id`** 컬럼 추가(nullable, `default
  auth.uid()`). 로그인 없이 쓰면 null(진짜 익명, 영구 수정불가), 로그인 상태로 쓰면 자동으로
  채워짐 — **"익명"으로 표시해도 내부적으로는 계정과 연결**돼서 나중에 본인이 찾아 수정/삭제
  가능.
- 글쓰기/댓글 작성 시 로그인 상태면 **"익명으로 쓰기" / "{카카오닉네임}(으)로 쓰기"** 선택
  가능 (`app/community/write/page.tsx`, `app/community/[id]/page.tsx`).
- **수정·삭제**: 게시글 상세 화면에서 본인 글/댓글에만 "수정"·"삭제" 버튼. RLS로 서버에서도
  `auth.uid() = user_id`만 되게 이중 방어. 로그인 상태에서는 **브라우저의 인증된 supabase
  클라이언트로 직접** insert/update/delete (Next.js API 라우트를 거치지 않음 — 세션의
  access token이 자동으로 실려야 `auth.uid()`가 정확히 잡히기 때문). 비로그인 흐름은 기존
  API 라우트(`/api/posts` 등) 그대로 유지.
  - `lib/communityClient.ts`: 이 "로그인 상태 직접 호출" 함수들 모음
    (`createPostAsUser`/`addCommentAsUser`/`updatePost`/`deletePost`/`updateComment`/
    `deleteComment`/`listMyPosts`/`listMyComments`)
- **"내 활동" 페이지** (`app/community/mine/page.tsx`): 로그인 시 커뮤니티 화면에 링크가
  뜨고, 내가 쓴 글/댓글 모아보기.
- 성별(`app/data/communityProfile.ts`)은 **온보딩엔 안 넣기로 함** (사용자가 명시적으로
  "그냥 넘어가자"고 결정) — 지금처럼 커뮤니티 글쓰기 화면에서만 로컬 저장으로 남음.

### 2-8. 목업/테스트 기능 정리

- **"간단히 관심분야로만 공고 찾기"(랜딩 화면, `jaripMatch.ts` 기반 완전 목업 데이터)를
  통째로 삭제함.** `app/data/jaripMatch.ts` 파일 자체도 지움.
- "🔎 실시간 공공데이터 API 결과 보기"는 **API 테스트용으로 남겨뒀고, 사용자가 나중에
  지울 예정**이라고 명시함 — 실제 서비스 로직(자격 진단)과 완전히 분리되어 있음.

## 3. 의도적으로 보류한 것

- **신원인증** (진짜 자립준비청년인지 확인) — 카카오 로그인은 계정 식별용일 뿐, 자격 검증
  수단이 아님. 나중에 별도로 설계 필요.
- **성별 항목의 계정 통합** — 커뮤니티 로컬 저장 그대로 두기로 함.
- **B2G 데이터 판매/재식별 지표화** — 명시적으로 거절 (2-5 참고).
- 멘토-멘티 커뮤니티 (자립완료자=멘토, 현재 자립준비청년=멘티) — 신원인증이 선행되어야 의미
  있어서 보류.
- 카카오 "간편가입"(카카오싱크) — 사업자등록 필요해서 해커톤 팀 상황상 사용 불가 확인,
  그냥 기본 카카오 로그인으로 진행.
- 커뮤니티 악용 방지(도배·신고 기능) — MVP 범위 밖으로 명시적으로 뺌.

   (security_invoker = on);` 필요 (PostgreSQL 15+). 지금은 신규 공고가 바로 approved라
   당장 위험하진 않지만, 나중에 검수 워크플로우 도입하면 재발.
3. **검수 UI** — 지금은 전부 SQL Editor 수동 (`docs/announcement-review-guide.md` 참고).
4. **`youthCenter` 소스 지역코드(zipCd) → 지역명 변환** — 이 소스만 거주지 필터 안 걸림.
5. **`protectionEndTypesApplicable`** — 항상 5종 반환하는 placeholder, 실제 배제 로직 필요.
6. **현재상태별 보기의 취업/미취업/기타 세분화** — DB에 `requiresEnrolled` 이진 플래그뿐이라

   추가로 뽑아내야 의미 있어짐.
7. **CRON_SECRET 환경변수 설정** — 지금 크론 라우트가 보호 없이 열려있음(선택적 보안 강화).
