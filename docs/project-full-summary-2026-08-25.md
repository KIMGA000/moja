## 1. 한 줄 소개

**모자(MOJA)** — 자립준비청년(보호시설·위탁가정에서 보호가 종료되어 자립을 준비/시작한 청년)을
위해, 흩어진 정부·지자체 지원 공고를 실시간으로 모아 조건에 맞는 것만 보여주고, 자격 여부를
진단해주고, 로그인하면 개인화된 정보를 계속 보여주고, 또래와 이야기 나눌 수 있는 익명 커뮤니티도
제공하는 웹서비스.

- **팀명**: 파란만 (AX-Ton 해커톤)
- **배포**: https://moja-khaki.vercel.app
- **저장소**: https://github.com/KIMGA000/moja (비공개)

## 2. 기획 여정 — 세 번의 피벗

지금의 "모자(MOJA)"에 도달하기까지, 딥리서치 기반으로 검토했던 아이디어가 두 번 더 있었습니다.
셋 다 구조가 같습니다: **"자격이 되는 지원 제도가 이미 있는데, 당사자가 몰라서/신청할 여력이
없어서 놓친다"**는 동일한 문제 패턴을, 서로 다른 타겟에 적용해본 것입니다.

### 2-1. 시도 1 (2026-08-04) — 청년 마음 연결 서비스

> **타겟**: "본인이 아직 '나는 고립·은둔 청년/우울증 환자다'라고 스스로 규정하지 못했거나,
> 규정했더라도 기존 지원사업에 신청할 심리적·행정적 에너지가 없는 19~34세 청년"

- **문제 규모**: 청년 고립·은둔 추정 약 53.8만 명(2년간 2배 증가), 사회경제적 비용 연
  5조 2,870억 원. 우울감 경험자 중 전문 상담 경험 비율은 27.3%로 여전히 낮음.
- **기획**: 3분 익명 자가진단(사회적 고립·회피·우울 선별) → 경계선 위험군 판별 →
  지역/상태별 정부 지원사업(서울시 고립은둔청년 지원사업, 마음건강 바우처 등) 자동 매칭·안내.
- **경쟁 분석 결론**: "①자가진단 → ②위험군 판별 → ③지원사업 자동 매칭"을 하나의 흐름으로
  엮은 서비스는 시장에 없었음. 다만 이후 팀 논의를 거쳐 **더 구체적이고 검증하기 쉬운 타겟**으로
  방향을 좁히기로 하고 다음 아이디어로 넘어감.
- 원본: [research-youth-isolation-mentalhealth.md](./research-youth-isolation-mentalhealth.md),
  [research-existing-services-competitor-analysis.md](./research-existing-services-competitor-analysis.md),
  [service-development-plan.md](./service-development-plan.md)

### 2-2. 시도 2 (2026-08-14) — 사장님 지원사업 알리미

> **타겟**: 자격이 있는 정부·지자체 지원사업을 몰라서, 혹은 영업 중 서류·신청 절차를 처리할
> 시간·디지털 역량이 없어서 놓치는 요식업 소상공인

- **문제 규모**: 2025년 소상공인 정책자금 3.77조원, 정책금융 전체 26.5조원 — "사업이 없다"가
  아니라 "사장님이 존재·자격·신청법을 모르거나 처리할 시간이 없다"는 접근성 격차. 고령화와
  영업시간 구속 때문에 요식업은 이 격차가 특히 큼.
- **기획**: 1분 익명 자가진단(업종·매출·지역·사업자 등록 기간) → 정책자금·배달비 지원·희망
  리턴패키지 등 자동 매칭 → 마감 임박 알림.
- **경쟁 분석 결론**: 정부 공식 채널·민간 AI 매칭 엔진·세무사향 B2B 알림·요식업 특화 운영툴 등
  5개 카테고리가 각각 따로 존재하고, "요식업 특화 자가진단→매칭→신청안내"를 하나로 묶은
  서비스는 없었음. 다만 팀은 최종적으로 **자립준비청년** 쪽으로 다시 피벗함(요식업보다 팀원의
  실감·문제의식이 강하고, 자격 판정 로직이 명확한 법령에 근거할 수 있어 MVP 정확도를 높이기
  좋다고 판단).
- 원본: [research-foodservice-smallbiz-support-gap.md](./research-foodservice-smallbiz-support-gap.md),
  [research-foodservice-smallbiz-competitor-analysis.md](./research-foodservice-smallbiz-competitor-analysis.md),
  [service-development-plan-foodservice-support.md](./service-development-plan-foodservice-support.md)

### 2-3. 최종 — 모자(MOJA), 자립준비청년 (2026-08-14~)

같은 "있는데 안 닿는 지원" 문제를, **자립준비청년**에게 적용. 이 타겟은 ①법적으로 지원 자격·
기한 기준(아동복지법 제38조)이 명확해서 자격 판정 로직을 정확하게 만들 수 있고, ②보호종료라는
단일 사건을 기준으로 관련 지원이 한 사람에게 몰려있어서 "매칭"의 가치가 크다는 점에서 최종
선택됨. 이후의 모든 개발은 이 방향으로 진행됨 (아래 5장 타임라인 참고).

## 3. 지금의 모자(MOJA)는 무엇인가

- **대상 사용자**: 자립준비청년 (보호시설·위탁가정에서 보호가 종료되어 자립을 준비/시작한 청년)
- **핵심 가치**:
  1. 흩어진 정부 지원 공고(8개 공공 API)를 실시간으로 모아 DB에 저장
  2. 온보딩 12문항으로 자격 여부를 진단(가능성 높음/확인 필요/해당 안 됨)
  3. 로그인하면 진단 결과가 저장되고, 개인화된 현황(D-day, 관심분야 등)을 계속 보여줌
  4. 관심 공고를 저장(북마크)하고, 지역·현재상태·관심분야·상시/기간별로 걸러볼 수 있음(로그인
     회원 전용)
  5. 또래와 이야기 나눌 수 있는 커뮤니티(글쓰기·댓글은 로그인 필요)
- **의도적으로 신원인증은 하지 않음**: 카카오 로그인은 "이 데이터가 같은 사람 것"임을 보장하는
  최소 계정 계층일 뿐, "진짜 자립준비청년인지" 확인하는 수단이 아님 (9장 참고).

## 4. 기술 스택

- **프론트엔드**: Next.js 15 (App Router) + React 19 + TypeScript, 클라이언트 컴포넌트 위주
- **백엔드/DB**: Supabase (PostgreSQL + Auth), Row Level Security로 접근 제어
- **인증**: Supabase Auth의 Kakao Provider (OAuth)
- **배포**: Vercel (+ Vercel Cron으로 매일 새벽 5시 KST 자동 재동기화)
- **외부 데이터**: 공공데이터포털·고용24·온통청년 등 8개 정부 Open API

## 7. 데이터 파이프라인 & 검수 체계

- 8개 공공 API → `lib/govApis.ts`에서 공통 타입(`WelfareItem`)으로 변환 → `classify.ts`가
  저장 시점에 분류 컬럼(지역/재학요건/관심분야/#태그 등) 계산 → 소스별 테이블 8개에 upsert
- **검수는 전부 수동**(Supabase SQL Editor). 신규 동기화 공고는 검수 없이 바로 `approved`로
  노출되고, 검수팀은 "이미 노출된 것 중 잘못된 걸 찾아 `rejected`로 내리는" 역할
- ⚠️ **분류 컬럼을 고쳐도 화면에 반영 안 됨**: 실제 자격 판정(`realMatch.ts`)은 여전히 매
  요청마다 원문 텍스트를 직접 재검사하고, DB 분류 컬럼(3~7번 탭이 쓰는 것)과는 별개 로직임 —
  가장 시급한 개선 과제로 남아있음
- ⚠️ `protection_end_types_applicable`은 항상 5종 전부를 반환하는 placeholder (배제 로직 미구현)
- 원본: [announcement-review-guide.md](./announcement-review-guide.md)

## 8. 주요 의사결정과 그 이유

| 결정 | 이유 |
|---|---|
| **B2G 데이터 판매 거절** | 관심공고·클릭 데이터를 가공해 정부에 팔거나, 지역+나이로 자립준비청년을 식별하는 지표로 판매하자는 제안이 있었으나 명시적으로 거절함. 취약계층 재식별 위험, 개인정보보호법상 목적외이용 문제, 서비스 신뢰 붕괴 우려. 대신 개인 식별 없는 내부 집계 통계까지만 허용 |
| **신원인증 보류** | 카카오 로그인은 계정 식별용일 뿐 "진짜 자립준비청년인지" 확인하는 수단이 아님. 별도 설계가 필요해 후속 과제로 보류 (멘토-멘티 커뮤니티 등이 이 위에 얹혀야 함) |
| **카카오 "간편가입"(카카오싱크) 미사용** | 사업자등록이 필요해 해커톤 팀 상황상 사용 불가 → 기본 카카오 로그인으로 진행 |
| **온보딩을 로그인으로 대체할 수 없음** | 보호종료 유형·거주지역·재학상태 등은 카카오가 원천적으로 알 수 없는 정보라, "내 자격 정밀 진단하기"는 로그인 여부와 무관하게 항상 필요 (로그인 + 최초 1회 온보딩 조합이 맞는 구조) |
| **커뮤니티 글쓰기 로그인 필수화** | 익명 자유글쓰기 남용 방지를 위해, 글쓰기·댓글은 로그인 필수로 전환(닉네임 표시는 익명/실명 선택 가능, 계정에는 항상 연결) |
| **성별 항목 온보딩 미포함** | 커뮤니티 글쓰기 화면의 로컬 저장 값으로만 남기고 정식 온보딩 질문에는 넣지 않기로 결정 |
| **release 브랜치 네이밍을 기능 중심으로** | `release/날짜-해시`보다 `release/기능명`이 어느 배포에 어떤 기능이 들어있는지 더 잘 드러남 |

## 9. 알려진 한계 & 백로그

### 9-1. 알려진 한계 (반영은 됐지만 남은 문제)
- 매칭결과 탭이 여전히 DB 분류 컬럼을 안 쓰고 원문 텍스트를 매번 재검사함 (7장 참고)
- `announcements_all` 뷰가 anon 키로 직접 조회되면 `pending` 공고까지 노출됨
  (`security_invoker = on` 필요)
- 현재상태별 필터는 "재학 요건 있음/없음" 이진 플래그만 있어서, 세분화된 취업 상태 필터링은
  아직 불가능
- `youthCenter` 소스는 지역코드→지역명 변환이 없어 거주지 필터가 안 걸림
- `protection_end_types_applicable`이 항상 5종 전부를 반환하는 placeholder
- `description_tags` 키워드 사전(24개)이 임의 큐레이션이라 빠진 단어가 있을 수 있음
- `CRON_SECRET` 환경변수 미설정 (코드는 대응해뒀지만 값만 안 넣은 상태)
- `main`과 `dev`의 코드 격차 (의도적으로 그대로 둔 상태 — README만 최신화됨)

### 9-2. 더 개발하면 좋을 것 (백로그)
- **로드맵/지속 알림 기능**: 가입 시 정보 기반 지속 알림이나 "다음 단계" 로드맵 UI (요청됐지만
  미구현)
- **멘토-멘티 커뮤니티**: 자립완료자=멘토, 현재 자립준비청년=멘티. 신원인증이 선행돼야 의미 있음
- **신원인증 설계**: 위 항목들의 전제조건
- **`realMatch.ts`를 DB 분류 컬럼 기반으로 전환**: 검수 워크플로우가 실제로 의미를 가지려면 필수
- **검수 UI**: 지금은 SQL Editor 수동 작업
- **커뮤니티 악용 방지**(도배·신고): MVP 범위 밖으로 명시적으로 제외
- GitHub Collaborator 팀원 초대

## 10. AI 활용 방식 (발표용 포인트)

이 프로젝트는 전 과정에서 Claude Code를 페어 프로그래머로 활용했습니다. 실제 사용 패턴을
요약하면:

1. **현황 진단 요청**: "지금 매칭이 임의로 되는 건지, API 호출인지 DB 조회인지" 등 구현
   방식을 먼저 설명받고 다음 지시를 결정
2. **인프라·협업 셋업 지시**: GitHub 저장소 생성, 브랜치 전략(`main`/`dev`/`release/*`) 수립,
   배포 트러블슈팅
3. **기능 구현 지시 → 검증 요구**: 카카오 로그인처럼 외부 서비스 연동은 콘솔 설정 캡처를
   그대로 붙여넣으며 트러블슈팅을 반복
4. **아이디어 발산 후 스스로 브레이크**: 로드맵 알림·멘토링 커뮤니티 등 확장 아이디어를 먼저
   던지고, B2G 데이터 판매처럼 위험한 방향은 스스로 재검토해서 명시적으로 거절
5. **법적 근거 검증 요구**: "5년 이내" 같은 기준이 실제 법령에 있는지 재차 확인시킴 (아동복지법
   제38조)
6. **마무리 문서화 지시**: 인계문서·요구사항 트래커·AI 활용 프롬프트 모음·이 종합정리 문서까지,
   세션 마무리마다 문서화를 지시해 다음 세션(또는 다른 AI)이 맥락을 이어받을 수 있게 함
7. **재현 가능성 확보**: [reproduce-prompt.md](./reproduce-prompt.md)에 "처음부터 똑같이
   만드는 프롬프트"를 정리해둬서, 다른 팀원이 API 키만 발급받으면 동일한 구조로 재현 가능

전체 프롬프트 원문은 [ai-usage-prompts-2026-08-25.md](./ai-usage-prompts-2026-08-25.md)에서
확인할 수 있습니다.
